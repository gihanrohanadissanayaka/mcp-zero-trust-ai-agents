# MCP Hub Integration Instructions

## MANDATORY: Use Case Documentation Rules

### Development Workflow (CRITICAL ORDER)

1. **Plan Features**: Create use cases with business context (user story, acceptance criteria)
2. **Develop APIs**: Implement actual endpoints with real functionality
3. **Document APIs**: Use `api_document_link` to connect working APIs to use cases with examples
4. **Test & Validate**: Ensure documentation matches actual implementation

### NEVER document endpoints before they're implemented - this leads to inaccurate documentation.

## Phase 1: Feature Planning

Use `usecases_upsert` for initial planning:

```json
{
  "id": "uc_project_feature_name",
  "projectId": "prj_project_name",
  "title": "Feature Title",
  "description": "What this feature will do",
  "userStory": "As a [role] I want [goal] so that [benefit]",
  "acceptanceCriteria": ["Requirement 1", "Requirement 2"],
  "businessValue": "Why this matters to business",
  "backend": {
    "repos": ["repo_project_api"],
    "endpoints": [],  // EMPTY during planning phase
    "collections": [
      {
        "name": "table_name",
        "purpose": "Data this will store",
        "operations": ["CREATE", "READ", "UPDATE", "DELETE"]
      }
    ],
    "filesToModify": ["planned/files.js"]
  },
  "frontend": {
    "repos": ["repo_project_web"], 
    "routes": ["/user/route"],
    "components": ["Component.js"],
    "userFlows": [
      {
        "flow": "User interaction",
        "steps": ["Step 1", "Step 2"]
      }
    ]
  },
  "tags": ["relevant", "tags"]
}
```

## Phase 2: API Implementation

After implementing working APIs, use `api_document_link`:

```json
{
  "useCaseId": "uc_project_feature_name",
  "endpoint": {
    "path": "/api/users",
    "method": "POST",
    "description": "Create new user account",
    "requestExample": {
      "name": "John Doe",
      "email": "john@example.com",
      "role": "user"
    },
    "responseExample": {
      "id": "user_123",
      "name": "John Doe", 
      "email": "john@example.com",
      "role": "user",
      "createdAt": "2025-10-02T10:00:00Z"
    },
    "authentication": "bearer",

  },
  "testResults": {
    "status": "working",
    "testDate": "2025-10-02",
    "notes": "All validation working correctly"
  }

```

## MCP Tools by Development Phase

### Planning Phase:
- `usecases_search` - Check existing features
- `usecases_upsert` - Create feature plan with business context
- `analysis_impact` - Analyze technical requirements

### Implementation Phase:
- Build actual APIs with real functionality
- Test endpoints thoroughly

### Documentation Phase:
- `api_document_link` - Document working APIs with real examples
- `usecases_get` - Verify complete documentation

### Maintenance Phase:
- `usecases_upsert` - Update business requirements
- `api_document_link` - Update API examples when changed

## CRITICAL RULES

1. **Business First**: Always start with user story and business value
2. **Code Then Document**: Only document APIs after they're working
3. **Real Examples**: Use actual request/response from working APIs
4. **Complete Context**: Include authentication, status, and implementation files
5. **Frontend Ready**: Response examples should match frontend needs

## Validation Checklist

### For Planning (usecases_upsert):
- Clear user story and business value
- Database collections planned
- Frontend user flows described
- Empty endpoints array (until implemented)

### For API Documentation (api_document_link):
- Working API endpoint tested
- Real request/response examples
- Authentication requirements specified
- Implementation file referenced
- Status marked as 'working'

---

**Key Principle**: Document reality, not intentions. APIs must exist and work before being documented in use cases.
